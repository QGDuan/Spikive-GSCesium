# UI 设计系统与工程规范

## 1. 目的与边界

本规范是 Spikive GS 管理界面的唯一 UI 标准，用于统一卡片、字体、颜色、按钮、状态、间距和容器组织。后续新增界面必须复用这里定义的令牌与基础组件，不再为单个页面复制一套视觉样式。

UI 与三维系统保持清晰边界：React 负责场景、标签、状态、表单和性能信息；PlayCanvas 负责 GS、体素调试网格、世界空间标签与射线拾取。React 不创建 Canvas、GraphicsDevice、Renderer，也不保存空间计算真值。

## 2. 分层结构

```text
src/ui/contracts.ts        业务界面的类型与回调契约
src/ui/theme.css           唯一设计令牌：颜色、字体、间距、圆角、阴影、尺寸、层级
src/ui/primitives.tsx      通用原语：Button、UiContainer、Icon、StatusMark、SectionHeading、EmptyState
src/ui/ScenePanel.tsx      场景导入、切片、体素和场景卡片
src/ui/LabelPanel.tsx      标签列表、筛选、详情与编辑卡片
src/ui/MissionPanel.tsx    场景绑定的航线创建、参数、规划与删除
src/ui/PerformanceCard.tsx 只读性能卡片
src/ui/AppShell.tsx        只负责导航与区域组合
src/styles.css             原语样式、业务排版与响应式布局，不定义新的主题值
```

数据结构、回调签名只放在 `contracts.ts`。格式化函数只放在 `format.ts`。业务组件不得反向承载 Renderer、数据库或空间算法。

## 3. 视觉语言

系统使用 SuperSplat 风格的黑色、灰阶和橙色：

- 黑色/深灰表达画布、导航、面板与卡片层级；
- 白色和灰色表达正文、次要信息与弱提示；
- 橙色只用于主操作、选中、焦点、运行状态和空间方向语义；
- 危险色只用于删除、不可恢复操作和明确错误；
- 不使用渐变、装饰色、发光大面积背景或过大的圆角。

所有颜色值只允许定义在 `src/ui/theme.css`。`styles.css` 和 TSX 不得写十六进制、RGB/RGBA 或内联视觉样式。需要新颜色时，先判断它是否具有跨组件语义；确认后增加一个 `--ui-color-*` 令牌，再由组件引用。

## 4. 字体与信息层级

- 普通界面使用 `--ui-font-sans`，覆盖 macOS、Windows 和中文字体回退；
- 坐标、版本、计数、文件大小和性能值使用 `--ui-font-mono`；
- 字号只使用 caption、helper、label、body、title、heading 六级令牌，字重只使用 medium、semibold、heading、bold 四级令牌；
- 页面标题不超过 heading，卡片标题不超过 title；
- 辅助说明不能通过更亮颜色抢占主信息，只使用 secondary、muted 或 faint；
- 禁止组件自行声明新的字体族和任意字号。

## 5. 统一容器

所有具有背景、边框、圆角或阴影的视觉卡片都必须使用 `UiContainer`，再选择固定语义变体：

| 变体 | 用途 | 当前实例 |
|---|---|---|
| `panel` | 一整块工作区 | 左侧场景管理、标签管理 |
| `floating` | 与视口叠加的独立卡片 | 右上巡检点、右下性能、底部状态 |
| `card` | 可重复的业务实体 | 单个场景卡片 |
| `subtle` | 面板内的弱分组 | PLY 导入、当前场景绑定 |

业务类只负责网格、内边距、对齐和内容布局，不得重复定义容器背景、通用边框、圆角和阴影。新容器若不能归入这四类，应先扩展设计系统并说明跨页面用途，而不是在业务 CSS 中临时添加一种卡片。

## 6. 按钮、状态与表单

普通操作使用 `Button`，按语义选用：

- `primary`：一个区域当前最重要的推进动作；
- `default`：普通动作；
- `active`：已开启的可逆显示状态，并同时设置 `aria-pressed`；
- `ghost`：低权重动作或取消；
- `danger`：永久删除确认。

按钮尺寸只有 default 和 compact。图标来自统一 `Icon` 集合。搜索提交、类型选择、筛选 Chip 和主导航可使用原生 button，但必须复用主题令牌、完整 hover/focus/active/disabled 状态和无障碍语义。

表单使用原生 input/textarea/fieldset，保证中文 IME、键盘和焦点行为。状态使用 `StatusMark`，空内容使用 `EmptyState`，区块标题使用 `SectionHeading`，禁止业务组件复制同类标记。

## 7. 页面和业务组织

- 主导航内部标识固定为 `scenes | labels | missions`，界面统一称“场景”“标签”“航线”，不再混用“数据”作为页面名称；
- 场景卡片只管理源 PLY、视觉切片、体素、显示状态和永久删除；
- 标签页只读绑定当前成功加载的场景，不能在标签页切换所属场景；
- 航线页同样只读绑定当前场景；起点、顺序标签、参数、规划和删除在独立页面管理，不塞回场景卡片；
- 标签创建、列表与文本/类型筛选在左侧；草稿、选中详情和编辑在右上独立巡检点卡片；
- 性能卡片固定在右下，只显示 FPS、可见 GS、系统 CPU、系统内存和 GPU 资源估算；WebGPU/WebGL2 位于顶部；
- 后端空间查询能力保留，但界面不显示“查询选中点周边”；
- 所有删除操作都使用行内二次确认，不把永久删除混入可逆的显示开关。

这些规则是业务信息架构，不应因视觉改版而改变。

## 8. 布局、输入与可访问性

- React 根层必须 `pointer-events: none`，只有可见导航和卡片恢复指针事件，避免遮挡 PlayCanvas 视口；
- 左侧工作区、右上巡检点和右下性能卡片使用统一布局令牌管理宽度与层级；
- 窄屏只重排和收紧容器，不复制一份移动端业务组件；
- 粗指针设备提高控件最小高度；
- 所有键盘焦点使用橙色轮廓；
- 尊重 `prefers-reduced-motion`；
- 文本溢出、长文件名、长标签名和错误信息必须可截断或换行，不能撑破容器。

## 9. 变更流程与检查表

新增或修改 UI 时依次检查：

1. 业务契约是否已经存在于 `contracts.ts`；
2. 是否可由现有 primitive 和 container variant 表达；
3. 是否只使用主题令牌，没有硬编码颜色、字体、圆角和阴影；
4. 是否保留默认、悬停、焦点、选中、禁用、忙碌、错误和危险状态；
5. 是否保持场景/标签归属、删除约束和 Renderer 边界；
6. 是否不遮挡空白三维视口的相机和拾取输入；
7. 是否在桌面、窄窗口和粗指针条件下仍可用；
8. 执行 `npm test` 与 `npm run build`，其中 UI 架构测试会阻止颜色越界、旧页面命名、卡片原语绕过和性能指标扩张。

## 10. 当前审计结论

本次重构前存在以下问题：颜色、字体、圆角和容器外观散落在单一 CSS；场景、标签、性能和应用壳集中在一个大组件；同类按钮与空状态重复实现；可见名称已改为“场景”但内部仍使用 `data` 和 `dataset-card`。

现已统一为主题令牌、基础原语、独立业务组件与轻量 AppShell；内部页签为 `scenes | labels | missions`，场景卡片类名统一为 `scene-card`。上传、切片、体素、显示、标签 CRUD/筛选/编辑、航线规划、性能监控和删除业务各自保持独立。
